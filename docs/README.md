# BEEZ에 넣을 테트리스 문서 (개정 2판)

2026-11-12 정리. 지난번(dev 프로젝트 20, 11-11)에 BEEZ가 던진 질문 22개의 답과 비비 지적 36건을 문서에 미리 반영하고, BEEZ가 문서를 읽는 방식에 맞게 형식을 고친 판이다. 원본(프로젝트 20의 첫 버전 v63~v66)은 `original/`에 그대로 있다.

## 1. 파일과 올리는 순서

| 순서 | 파일 | BEEZ 문서 종류 | 비비 검토 때 참고 자료 |
| --- | --- | --- | --- |
| 1 | 02-requirements.md | REQ_SPEC | 없음 → 바로 승인 |
| 2 | 03-erd.md | ERD | 요구사항(승인본) |
| 3 | 04-api.md | API_SPEC | 요구사항·ERD(승인본) |
| 4 | 01-plan.md | PLAN | 참고 종류가 아니라 순서 무관 |

- 비비 검토는 **승인된 문서만** 참고한다. 한꺼번에 올리면 서로 대조가 안 되므로 위 순서로 하나씩 승인한다.
- PATCH 지적은 반영·넘김을 정한 뒤 제출한다(안 정하면 409 `review_decisions_pending`).
- 승인 직후 기획 질문이 다시 만들어지는 동안(REFRESHING)은 답할 수 없다. 1~2분 기다린다.

## 2. 무엇을 고쳤나

**질문을 미리 없앰** — 지난번 질문 22개의 답을 해당 문서 본문에 넣었다. 예: 조작 키, 점수 적용 순서, 방해 줄 구멍·올라오는 시점, 동시 topout, 재접속 10초 동안의 처리, 방 상태 전이, 시리즈 재경기, 전적 갱신 대상, 부하 시험 조건, FE 규칙 AI, Refresh 쿠키, 빠졌던 엔드포인트 상세.

**비비 지적 반영** — 응답 봉투 표기, AI 경로가 상대 경로인지, 인증 예외, /users/me·경기 상세 응답, 폴백 조건(지연 + 오류), 3초 카운트다운, 점수 재계산, 카카오 API, 저장 정책 모순, 랭킹 동점 정렬, 1년 보존, 콤보·B2B 정의, 재방문율 집계, 닉네임 태그 발급, TTL·프레임 측정 기준.

**BEEZ 처리 방식에 맞춤**
- 역슬래시 이스케이프(`\_`, `\~`)와 노션 잔재(`&#91;embedded content…`)를 없앴다. 비비 인용문은 원문과 글자 하나까지 같아야 통과한다.
- 규칙 값은 요구사항 명세서 한 곳(GR·BR 번호)에만 적고 다른 문서는 번호로 가리킨다. 같은 규칙을 문서마다 다르게 적어 생기던 일관성 지적을 막는다.
- 엔드포인트·STOMP 주소마다 절을 하나씩 두었다. AI 설계 초안은 "엔드포인트 하나에 항목 하나"로 뽑는데, 지난번에는 상세가 7개뿐이라 API 항목이 6개만 나왔다.
- 기능 요구사항을 26개에서 15개로 묶었다(아래 4절).
- 문서 안에서 어긋나던 값을 하나로 맞췄다. 예: 라운드 수 1·3(지난 답 1·3·5와 충돌), matches 고유키에 attempt_no 추가(재경기 때 같은 라운드 번호 충돌).

## 3. 제가 정한 것 — 확인 필요

지난 답변과 원본이 서로 달랐거나 어디에도 값이 없던 곳이다. 구현량이 적고 검증하기 쉬운 쪽을 골랐다.

| 항목 | 고른 것 | 버린 것 |
| --- | --- | --- |
| 친구 대전 서버 검증 | lock마다 블록·위치·줄 수를 받아 검사·재계산(BR-05), 이동 경로는 검사 안 함 | 지난 답 89: 입력 이벤트를 모두 보내고 서버가 보드를 재연산 |
| 싱글·AI 점수 검증 | 상한 검사, 어기면 저장하되 랭킹 제외(BR-07) | 지난 답 151: 입력 기록 재생으로 재계산 |
| 라운드 수 | 1 또는 3 | 지난 답 150: 1·3·5 |
| Refresh 토큰 | HttpOnly 쿠키 + 회전(지난 답 149) | 원본: 로그인 응답 본문에 refreshToken |
| 보드 크기 | 22행(위 2행 숨김), board 문자열 220자 | 원본: 20행·200자 |
| 방해 줄 구멍 | 공격 한 묶음은 같은 열(holeColumn 하나) | 원본 API: 줄마다 holeColumns |
| 같은 닉네임 재로그인 | 새 게스트 계정(이어 받기는 카카오로) | 정의 없음 |

새로 정한 값: 낙하 간격 표, 고정 지연 500ms·15회, 자동 반복 167/33ms, T-스핀 3코너·미니 없음, 무승부 판정 100ms, AI 탐색 깊이·재생 간격, FE 규칙 AI 가중치, 랭킹 합성 점수, 보존 배치 매일 04:00, 7-bag 난수 생성기(mulberry32).

ERD 추가: matches.attempt_no·end_reason·ranked, game_rooms.close_reason, user_stats 랭킹 인덱스, Redis 키 3개(user:{id}:room, 끊김 타이머, 랭킹 순번).
API 추가: 카카오 2개, 15개 REST 전부 상세, STOMP PLAYER_RECONNECTED·REMATCH_CHANGED·RESYNC(/user/queue/state), 오류 코드 10개.

## 5. 남은 위험

- **부분당 15개 상한** — BEEZ는 문서를 약 6,000자씩 나눠 부분마다 항목을 최대 15개 뽑는다. 요구사항 명세서는 두 부분으로 나뉘고 각 부분에 후보가 20개 남짓이라, AI가 몇 개를 합칠 수 있다(지난번에도 방 요구사항 4개가 한 항목으로 합쳐졌다). 4절 표로 확인한다. 상한은 `beez.planning.part-max-items`(서버 기본 15)이며 dev에서는 바꾸지 않았다.
- **설계 항목 증가** — 40개에서 70개 안팎으로 늘면 작업 분해와 검증의 입력이 커진다. 검증 예산 30초에서 지난번 큰 입력의 여유가 0.4~3.3초였으니 첫 검증 몇 건은 시간을 재며 진행한다.
- **문서가 길어짐** — 비비 검토(특히 요구사항·ERD를 참고하는 API 명세)가 지난번보다 오래 걸린다.
- 질문이 0개가 되지는 않는다. 새로 정한 값에서 다시 물을 수 있다.
